### A bug this check caught

The first run of `verify_model.py` failed on PR-AUC by 0.0015. That was not tolerance
drift — it was a real defect. `Scorer.score_batch` called
`frame[column].astype("category")`, and pandas derives category *codes* from whichever
values happen to be present in the batch. LightGBM matches categorical features by
integer code, so scoring a five-row candidate batch assigned `error_code` a different
code than training had for the same string. Silently: a plausible probability, quietly
wrong, and exactly the class of failure that survives to a demo.

Fixed by pinning the level lists at training time into `feature_names.json` and using
`pd.Categorical(values, categories=levels)` at inference. An unseen level now lands as
NaN — which is what LightGBM expects for an unknown category — rather than being
silently reassigned to some other value's code. Re-running the evaluation after the fix
produced identical arm numbers, so the Stage 4 null result is unaffected; the fix was
still necessary, because the correctness of the treatment arm should not depend on which
candidates happened to be in a batch.
